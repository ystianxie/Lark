# Lark 翻译组件实施计划

> 目标：在 Lark 中实现一个以快速文本翻译为核心、可扩展到划词翻译和截图 OCR 翻译的组件。优先保证唤起速度、结果反馈和失败可恢复，再增加识别能力。
>
> 适用范围：Windows 优先，Tauri 2 + React + Rust，翻译能力作为插件/组件接入。
>
> 方案日期：2026-10-03
>
> 当前状态：阶段 0 已完成，具体任务见 [翻译组件-TODO.md](翻译组件-TODO.md)，规格见 [翻译组件-阶段0规格.md](翻译组件-阶段0规格.md)。

## 一、总体原则

1. 翻译配置、翻译服务、运行面板、输入来源和 OCR 分层，避免把 API 调用写死在 UI 中。
2. 普通翻译优先使用响应快的服务；AI 翻译作为可选 Provider 或增强操作，不阻塞首屏。
3. 所有外部请求都支持超时、取消、错误展示和重试；结果返回顺序不能覆盖较新的请求。
4. 先完成可手动输入的翻译闭环，再接入剪贴板、划词和截图，逐步扩大系统权限。
5. API Key 等敏感配置不写入插件源码或前端日志，保存方式由 Tauri/Rust 统一管理。

## 二、阶段划分

### 阶段 0：边界与验收标准

明确支持的语言、Provider、快捷键、窗口行为、密钥保存方式和响应时间预算。定义最小闭环：输入文本后可在合理时间内看到译文，并能复制结果。

### 阶段 1：应用设置组件——配置页面与持久化

在“应用设置”中增加翻译配置页面。先完成配置模型、默认值、表单校验、敏感字段处理和持久化，再接入真实请求。

建议配置包括：默认 Provider、源语言、目标语言、快捷键、请求超时、是否自动读取剪贴板、是否启用 AI Provider，以及各 Provider 的必要参数。保存必须具备版本兼容和失败回滚。

### 阶段 2：翻译组件 Panel 页面

实现独立的翻译 Panel，支持原文输入、目标语言切换、翻译中状态、错误状态、结果复制、清空和重新翻译。Panel 应可复用，不因每次翻译重新初始化运行时。

本阶段先使用 Mock Provider 验证交互，再接真实服务。需要同时确定窗口尺寸、焦点、关闭、置顶和快捷键唤起行为。

### 阶段 3：Provider 与请求运行时

建立统一 Provider 接口和请求编排层，接入至少一个快速翻译服务。Provider 负责协议、签名和响应解析；运行时负责超时、取消、重试、缓存、流式响应和旧请求淘汰。

AI Provider 作为可选能力接入，并明确“首屏快速翻译”和“AI 优化/重译”的不同入口。

### 阶段 4：文本输入输出能力

先实现剪贴板读取、翻译结果复制和结果写回，再实现划词翻译。划词流程应尽量做到：快捷键唤起、读取当前选区、自动翻译、结果可复制或替换原文。

需要处理焦点恢复、剪贴板来源变化、无选中文本、长文本限制、重复触发和目标应用拒绝粘贴等情况。

### 阶段 5：截图 OCR 翻译

采用“截图后直接 OCR 翻译”的精简流程：快捷键进入截图选择、截取区域、调用 OCR、将识别文本送入翻译、展示结果。第一版不做复杂版面还原和文档翻译。

OCR 结果应保留可编辑入口；识别失败时保留截图并允许重试。优先评估本地 OCR，云端 OCR 作为可配置 Provider，不默认上传用户截图。

## 三、推荐验收顺序

1. 设置可保存、重启后配置仍存在。
2. Panel 可用 Mock 数据完成输入到结果的完整交互。
3. 真实 Provider 在超时、失败、取消和重复请求下行为正确。
4. 剪贴板读取和结果复制稳定，不破坏用户原剪贴板。
5. 划词翻译可完成读取、翻译和写回。
6. 截图 OCR 翻译在中英文短文本上可用，并且失败可恢复。

## 四、暂不纳入第一版

复杂排版 OCR、表格结构恢复、文档批量翻译、语音识别、翻译记忆库、多 Provider 并行对比和自建模型。这些能力应在快速翻译闭环稳定后再评估。
