# 文件系统监听与文件索引增量更新：三阶段实施计划

> 目标：让 `file_index` 在首次全量扫描后，能够随文件系统的新增、修改、删除和重命名自动同步。
>
> 适用范围：Lark 当前 Tauri 2 + Rust 架构，优先保证 Windows，再验证 macOS。
>
> 计划日期：2026-09-19
>
> 最近进度更新：2026-09-20

## 1. 现状与总体策略

当前已接入文件系统 watcher，并通过批处理增量更新 `file_index`；`create_file_index_to_sql` 仍负责 generation/staging 全量重建。全量扫描与 watcher 已改为读取 `local_file_search_paths`，不再默认扫描或监听整个系统盘。配置保存后的 watcher 热重载和索引校正尚未实现。

总体采用“全量扫描兜底、运行时增量同步”的结构：

```text
应用启动/手动重建 ──> 全量扫描 ──> 建立基准索引
                                      │
配置目录/磁盘 ──> 文件 watcher ──> debounce 批处理 ──> 增量 SQL 更新
                                      │
                       监听错误/队列溢出 ──> 重新全量扫描
```

不建议把监听逻辑直接堆入 `main.rs`。建议新增 `api/file_watcher.rs` 或 `utils/file_watcher.rs`，由独立的 `FileWatcherHandle` 管理线程、停止信号和重建请求；索引写入能力集中在 `IndexSQL`。

## 1.1 当前实施进度（2026-09-20）

- [x] watcher 模块、事件归一化、debounce、批量 SQLite 增量写入已接入。
- [x] 文件包含路径已经落入配置、设置界面、全量扫描和 watcher 启动流程。
- [x] 首次启动时仅在配置为 `None` 时生成默认包含路径；后续不会重复初始化。
- [x] 空数组代表显式关闭文件扫描和监听，不会回退到所有磁盘。
- [x] 排除路径优先于包含路径，隐藏目录、Remove 和跨边界 rename 事件已补充处理。
- [ ] 保存设置后，当前运行中的 watcher 尚不会自动停止并重建；目前需要重启应用后生效。
- [ ] watcher 重载后尚未执行“删除旧范围索引 + 扫描新增范围”的一致性校正。

## 2. 分阶段目标总览

| 阶段 | 目标 | 结果 | 预计工作量 |
| --- | --- | --- | --- |
| 第一阶段：MVP | 新增/修改/删除能够自动同步 | Windows 本地目录可用，异常可手动重建 | 1～2 天 |
| 第二阶段：稳定版 | 重命名、配置变化、批量事件和生命周期完整 | 日常使用稳定，跨平台逻辑统一 | 3～5 天 |
| 第三阶段：生产级 | 异常恢复、性能、跨平台和一致性验证 | 可长期后台运行并可诊断 | 3～7 天 |

以上时间不包含 Cargo 依赖下载、真实机器兼容性排查和可能的数据库迁移时间。

## 3. 第一阶段：可用 MVP

### 3.1 目标与边界

- 引入成熟的跨平台 watcher（优先评估 `notify`/`notify-debouncer-mini`）。
- 先支持 Windows 本地固定目录；macOS 保留编译路径，但不把兼容性作为首个验收门槛。
- 支持 create、modify、remove；rename 可以先按 remove + create 处理。
- 保留现有全量扫描，监听器只负责扫描完成后的增量维护。
- 不做复杂 UI，只输出日志并复用现有索引完成事件。

### 3.2 实施任务

1. 依赖与模块：加入 watcher 依赖，创建 `file_watcher` 模块和 `FileWatcherHandle`。
2. 监听根目录：读取 `local_file_search_paths`；`None` 首次启动时初始化常用用户目录和非系统固定盘，`Some([])` 表示明确不监听，不允许回退到全盘监听。
3. 过滤规则：复用扫描逻辑中的隐藏文件、排除目录、排除扩展名判断，避免监听和全量扫描规则不一致。
4. 事件归一化：把 watcher 事件转换为内部 `Created/Changed/Removed`，忽略无法转换为路径的事件。
5. 增量数据库接口：为 `IndexSQL` 增加按路径的 upsert、delete，以及必要的路径查询；插入数据时生成标题、类型、拼音和首字母。
6. 批量处理：按短时间窗口合并事件，单批事务写入 SQLite，避免每个事件单独提交。
7. 生命周期：在 Tauri `setup` 中启动并通过 `app.manage` 持有句柄，退出时停止；防止重复启动。
8. 失败提示：监听初始化失败、数据库写入失败时打印明确日志，并保留“重建索引”命令作为恢复手段。

### 3.3 MVP 验收标准

- 启动并完成全量扫描后，新建文件在一次 debounce 周期后可搜索。
- 修改文件名或文件内容相关元数据后，索引结果不产生重复记录。
- 删除文件后，搜索不到该路径。
- 批量复制一批文件时，应用不明显卡顿，SQLite 无锁死。
- 关闭应用后 watcher 线程能够退出；重新启动不会创建多个监听线程。
- 监听失败不会阻止应用启动，且日志明确提示需要重建索引。

### 3.4 MVP 暂不解决的问题

网络盘、移动盘拔出、队列溢出、精确 rename 语义、配置热更新和 macOS 全面验收留到后续阶段。

## 4. 第二阶段：稳定版本

### 4.1 目标

让监听器与现有扫描配置、数据库 generation 机制和 Tauri 生命周期形成完整闭环，覆盖真实日常操作。

### 4.2 实施任务

1. **准确处理 rename**：维护旧路径到新路径的映射；无法确认时安全地执行删除旧路径、重新扫描新路径。
2. **目录事件展开**：目录创建、移动或删除时，对目录内容进行受控扫描/删除，而不是只更新目录本身。
3. **统一扫描器**：抽取“单路径转 `FileIndex`”和过滤逻辑，供全量扫描与增量事件共同调用。
4. **配置热更新**：保存索引设置后停止旧 watcher，重新计算监听根目录和过滤器；配置变更后执行一次校正扫描。
5. **批处理与背压**：按 200～500ms debounce，限制单批事件数量；大批量变更时合并相同路径，只保留最终状态。
6. **索引并发控制**：复用或扩展 `FILE_INDEX_RUNNING`，避免全量重建与增量事务同时改写数据库。
7. **状态事件**：增加 `file_watcher_status`、`file_index_updated` 等事件，前端可显示“监听中/重建中/异常”。
8. **跨平台适配**：验证 Windows `ReadDirectoryChangesW` 后端和 macOS FSEvents 行为，统一路径规范化、大小写和分隔符处理。

### 4.3 稳定版验收标准

- 新建、复制、移动、重命名、删除文件和目录均能最终同步。
- 排除目录和扩展名在全量扫描、增量监听中表现一致。
- 保存监听范围配置后无需重启即可生效。
- 全量重建期间发生的文件变化不会在重建结束后丢失；至少能触发一次校正扫描。
- 前端能够区分“索引尚未建立”和“监听暂时异常”。

## 5. 第三阶段：生产级版本

### 5.1 目标

处理 watcher 不可靠或系统资源紧张时的恢复问题，并建立可验证、可诊断的长期运行能力。

### 5.2 实施任务

1. **队列溢出恢复**：收到 watcher overflow、根目录失效或不可恢复错误时，标记索引为 stale，停止增量写入并排队全量重建。
2. **启动一致性校验**：记录监听配置指纹和最近一次成功扫描时间；启动后对关键根目录做轻量校验，必要时自动重建。
3. **性能优化**：批量事务、路径去重、目录级合并、限制并发扫描；监控 SQLite 提交耗时和事件积压量。
4. **磁盘和权限变化**：盘符上线/下线、目录权限改变、网络路径断开后自动重试，不把暂时不可访问误判为删除。
5. **可观测性**：记录 watcher 启停原因、事件数量、丢失事件、重建次数和最后错误；必要时提供诊断命令或设置页面状态。
6. **一致性工具**：增加“校验索引”操作，对数据库路径与文件系统抽样或全量比对，并输出修复统计。
7. **测试矩阵**：覆盖 Windows 10/11、macOS、中文路径、长路径、大小写变化、Git checkout、解压大量文件、编辑器临时文件和网络盘。
8. **发布策略**：先默认启用本地目录监听；出现兼容性问题时允许按平台或配置关闭监听，保留手动重建。

### 5.3 生产级验收标准

- watcher 线程异常退出后能自动恢复或明确转入全量重建，不需要重启应用。
- 队列溢出不会造成静默索引缺失。
- 大批量变更期间 CPU、内存和 SQLite 写入保持可接受，搜索仍可用。
- 日志能回答“监听了哪些目录、漏了什么、何时重建、当前是否一致”。
- Windows 和 macOS 的核心增删改重命名场景均通过实机验收。

## 6. 推荐的代码拆分

```text
src-tauri/src/api/file_watcher.rs
  FileWatcherHandle
  WatchConfig
  FileEvent / NormalizedEvent
  debounce_and_coalesce()

src-tauri/src/api/explorer.rs
  scan_path_to_file_index()
  should_skip_file()/should_skip_dir()（抽取为共享函数）

src-tauri/src/utils/database.rs
  upsert_file_index_by_path()
  delete_file_index_by_path()
  delete_file_index_under_path()
  apply_file_index_batch()
```

`main.rs` 只负责初始化、托管句柄和注册命令，不负责解释 watcher 事件。

## 7. 主要风险与决策点

| 风险 | 影响 | 建议 |
| --- | --- | --- |
| 监听磁盘根目录事件量过大 | CPU、内存和 SQLite 压力 | 先限制配置目录；事件合并和批量事务必须优先完成 |
| watcher 丢事件 | 索引静默缺失 | overflow 一律标记 stale 并全量重建 |
| 全量重建与增量更新并发 | 数据被覆盖或丢更新 | 统一互斥状态，重建完成后做校正扫描 |
| 过滤规则分叉 | 索引反复出现被排除文件 | 抽取共享扫描/过滤函数 |
| 路径大小写和规范化差异 | 重复记录或删除失败 | 写库前统一 canonicalize/分隔符策略，并保留原始展示路径 |
| 跨平台行为不同 | macOS/Windows 结果不一致 | 第一阶段 Windows 优先，第二阶段开始实机验证 macOS |

## 8. 开工前的最终建议

建议先实施第一阶段，但在编码前先确认两个选择：

1. 首期监听范围是“配置中的目录”，还是沿用当前 Windows 的“所有磁盘根目录”；推荐前者。
2. 是否允许监听异常自动触发全量重建；推荐允许，但增加冷却时间，避免异常时反复重建。

第一阶段完成后再根据事件量和数据库写入耗时决定是否进入第二阶段，不建议一开始就把生产级恢复逻辑全部塞进 MVP。
