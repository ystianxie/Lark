## 1. 第一阶段：统一搜索会话

### 1.1 会话模型

- [ ] 定义 `SearchSession`，包含 `queryId`、查询文本、开始时间和取消信号。
- [ ] 使用单调递增 `queryId` 标识每次输入产生的搜索。
- [ ] 新查询开始时取消上一会话。
- [ ] 所有异步结果携带或绑定所属 `queryId`。
- [ ] UI 丢弃非当前 `queryId` 的返回。
- [ ] 窗口关闭、隐藏或搜索输入清空时结束当前会话。
- [ ] 防止组件卸载后异步结果继续更新 React 状态。

### 1.2 当前插件队列适配

- [ ] 保留 `src/pluginExecution.js` 的同 key 合并能力，避免创建第二套重复队列。
- [ ] 为执行任务增加 `AbortSignal` 或等价取消上下文。
- [ ] 对无法物理取消的调用实现逻辑过期和结果丢弃。
- [ ] 明确队列中 pending、running、cancelled、completed 的状态语义。
- [ ] 避免旧任务结束时删除同 key 的新队列状态。
- [ ] 为连续快速输入、执行中取消和异常返回补充测试。

### 1.3 结果稳定性

- [ ] 定义后台结果追加和重排规则。
- [ ] 用户尚未操作选择时，允许更高质量结果按规则合并。
- [ ] 用户已按方向键或鼠标选择后，保持结果 identity，不按数组下标保持。
- [ ] 当前结果消失时定义可预测的回退选择。
- [ ] 防止同一结果从多个 Provider 返回后重复显示。
- [ ] 为结果追加、去重和选中项稳定补充测试。

### 1.4 第一阶段验收

- [ ] 快速输入至少 20 次时，最终只展示最后查询结果。
- [ ] 人工制造旧查询晚返回，不会覆盖新结果。
- [ ] 单个 Provider 抛错不会清空其他 Provider 结果。
- [ ] 窗口关闭后不出现 React 状态更新警告。
- [ ] 后台结果加入时不抢占用户当前选择。

## 2. 第一阶段：Provider 快慢分流

### 2.1 Provider 契约

- [ ] 盘点并定义 Provider：应用、文件、命令、片段、剪贴板、插件及其他现有来源。
- [ ] 定义统一 Provider ID、模式、优先级和 `search()` 契约。
- [ ] 区分 `immediate` 与 `background`。
- [ ] 明确 Provider 是否支持取消、分页和增量返回。
- [ ] 明确空查询、单字符查询和普通查询的执行策略。
- [ ] 不让插件自定义跨 Provider 的最终排序权重。

### 2.2 初始分类

- [ ] 应用索引归入快速 Provider。
- [ ] 文件精确和标题前缀归入快速 Provider。
- [ ] 文件标题包含和路径包含根据实测决定快速或后台。
- [ ] 计算器、内置命令、文本片段归入快速 Provider。
- [ ] 剪贴板近期结果完成隐私和性能检查后归类。
- [ ] Python、网络、外部程序和 AI 查询归入后台 Provider。

### 2.3 超时和降级

- [ ] 为每个 Provider 定义软预算和硬超时，数值由基准测试校准。
- [ ] 软预算超时只记录诊断，不立即终止正确任务。
- [ ] 硬超时后丢弃结果，并保留可定位错误信息。
- [ ] 明确连续慢查询达到什么条件才自动降级。
- [ ] 自动降级必须允许用户或开发者恢复，不形成永久黑盒状态。
- [ ] 插件超时不能导致宿主搜索会话失败。

### 2.4 Provider 验收

- [ ] 本地快速结果不等待 Python 或网络插件。
- [ ] 关闭一个后台 Provider 不影响其他来源。
- [ ] Provider 耗时和错误可在诊断日志中按 ID 定位。
- [ ] Provider 顺序变化不改变相同分数结果的稳定顺序。

## 3. 第一阶段：性能预算和诊断

### 3.1 指标

- [ ] 记录热键按下到窗口可见耗时。
- [ ] 分别记录首次打开和后续打开耗时。
- [ ] 记录输入到第一批结果耗时。
- [ ] 记录输入到结果稳定耗时。
- [ ] 记录每个 Provider 的开始、完成、取消、失败和超时。
- [ ] 记录一次查询的结果重排次数。
- [ ] 记录过期结果丢弃数量。
- [ ] 记录插件激活和 Python/Sidecar 执行耗时。

### 3.2 隐私与开销

- [ ] 指标中不保存查询原文。
- [ ] 默认不保存完整文件路径、剪贴板内容和插件配置。
- [ ] 使用长度、数量、类型和耗时等聚合信息代替原始数据。
- [ ] 指标写入不得位于输入渲染关键路径。
- [ ] 为诊断导出定义明确字段和脱敏规则。

### 3.3 基准验收

- [ ] 在低配或目标最低配置 Windows 设备测试。
- [ ] 使用冷启动和热启动分别测试。
- [ ] 使用 1 万、10 万和可行时 100 万文件记录测试搜索。
- [ ] 使用无插件、正常插件和故意慢插件三组测试。
- [ ] 记录 P50、P95，不只记录单次最好结果。
- [ ] 将最终预算写回方案或专门性能文档。

## 4. 第二阶段：统一结果模型

### 4.1 数据模型

- [ ] 定义跨 Provider 的 `SearchResult`。
- [ ] 使用稳定 `id`/identity，不以数组位置标识结果。
- [ ] 定义结果类型、标题、副标题、图标和来源。
- [ ] 定义 `matchKind`、`matchScore` 和高亮范围。
- [ ] 定义一个结果的主 Action 和附加 Action。
- [ ] 明确同一路径、同一应用和同一命令的去重 identity。
- [ ] 为旧结果结构提供最小适配层，避免一次性重写所有 Provider。

### 4.2 排序器

- [ ] 保留文件搜索现有精确、前缀、包含和路径分层。
- [ ] 定义各 `matchKind` 的基础顺序。
- [ ] 定义 Provider 基础权重，但避免硬编码散落各组件。
- [ ] 定义同分结果的稳定排序键。
- [ ] 插件分数先归一化，再进入宿主排序。
- [ ] 防止后台结果因不可比较的超大分数始终抢占第一位。
- [ ] 为精确、前缀、拼音、包含和同分稳定性补充测试。

### 4.3 用户选择历史

- [ ] 设计聚合表或配置结构，保存 query 归一化信息、结果 identity、次数和最后选择时间。
- [ ] 不无限保存每次原始查询事件。
- [ ] 引入时间衰减，避免旧结果永久占优。
- [ ] 新安装应用和新插件结果不能被历史权重完全压制。
- [ ] 提供清除学习记录的设置或命令。
- [ ] 历史记录损坏时排序器退回静态规则。
- [ ] 为常用结果提升和衰减行为补充测试。

## 5. 第二阶段：插件信任边界

### 5.1 现状确认

- [ ] 文档明确当前 Blob `import()` 插件与宿主运行在同一 WebView Realm。
- [ ] 文档明确 Manifest 权限是能力声明，不等于安全沙箱。
- [ ] 盘点插件能访问的 `window`、DOM、网络、存储和 Tauri API 表面。
- [ ] 盘点现有插件是否依赖直接 DOM 操作或宿主内部对象。
- [ ] 根据盘点结果确定迁移兼容范围。

### 5.2 插件分级

- [ ] 定义“内置可信插件”。
- [ ] 定义“已审核 UI 插件”。
- [ ] 定义“普通第三方插件”。
- [ ] 在 Manifest 或安装元数据中记录来源和信任等级。
- [ ] 不允许普通插件自行声明为可信。
- [ ] 权限和信任等级变化需要显式迁移规则。

### 5.3 Worker 原型

- [ ] 制作无 DOM 的 JS 查询插件 Worker 原型。
- [ ] 使用结构化消息传递输入、结果、错误和取消。
- [ ] 验证 Worker 可以被强制终止。
- [ ] 限制 Worker 可调用的宿主能力，只通过消息代理授权 API。
- [ ] 验证插件无法直接修改主页面 DOM。
- [ ] 为 Worker 崩溃、超时、重复启动和热重载补充测试。

### 5.4 Sidecar/Python

- [ ] 复用现有 Python 执行入口，不新增平行解释器配置。
- [ ] 明确默认超时、取消和进程回收行为。
- [ ] 验证超时后子进程及其子进程是否真正退出。
- [ ] 限制并发 Python/Sidecar 数量，避免进程风暴。
- [ ] 定义 stdout、stderr 和协议解析的大小上限。
- [ ] 插件失败不得泄露其他插件配置或宿主敏感状态。

### 5.5 声明式 UI

- [ ] 先定义最小组件集合，不复制完整 React DOM 能力。
- [ ] 插件返回结构化 ViewSchema，由宿主渲染。
- [ ] Action 必须映射到受权限控制的宿主动作。
- [ ] 未知组件、未知 Action 和非法参数必须拒绝。
- [ ] 评估旧 UI 插件兼容策略，不默认永久支持任意 DOM 插件。

## 7. USN Journal 技术验证门槛

### 7.1 进入条件

- [ ] 现有 watcher 在应用离线期间无法满足变化恢复需求。
- [ ] 或大规模事件造成无法接受的积压/全量重建成本。
- [ ] 或启动一致性校验需要持久增量记录。
- [ ] 已有全量重建可以可靠作为 USN 失效回退。

以上条件至少一项由实测证明后，才进入 USN 实施。

### 7.2 原型任务

- [ ] 读取卷序列号、Journal ID 和当前 USN 范围。
- [ ] 持久化每卷 `journal_id` 和 `last_usn`。
- [ ] 读取并解析新增、删除、重命名等记录。
- [ ] 验证应用关闭期间的变化可以在下次启动恢复。
- [ ] 检测 Journal ID 变化和游标早于有效范围。
- [ ] 游标无效时回退现有全量重建。
- [ ] 明确 FAT/exFAT、网络盘和移动盘降级行为。
- [ ] 不让 watcher 与 USN 独立双写同一变化。
- [ ] 原型基准未显示明显收益时停止实施，不因竞品使用而强行合入。

## 8. FTS5/高级搜索评估门槛

- [ ] 收集现有查询无法满足的真实多词或长文本场景。
- [ ] 使用相同数据集比较现有分层 SQL 与 FTS5 的延迟和结果质量。
- [ ] 只把 FTS5 用作多词、描述或长文本补充层。
- [ ] 不替换应用/文件标题的精确和前缀路径。
- [ ] 测量 FTS 索引体积、构建耗时和增量更新成本。
- [ ] 如果收益不足，不新增 FTS 表和迁移。
- [ ] 向量搜索另立方案，不与 FTS5 评估捆绑。

## 9. 触碰式模块拆分

- [ ] 搜索会话实施时，将新增调度逻辑放入独立 search 模块，不继续堆入 `App.jsx`。
- [ ] 排序器实施时使用独立纯函数模块，避免散落 Provider 和 React 组件。
- [ ] 数据库搜索修改时，只拆分相关 `IndexSQL` 领域，不全面重写 `database.rs`。
- [ ] 设置项修改时按功能抽取子组件，不一次性重做整个设置页。
- [ ] `main.rs` 新增命令时优先将实现放入领域模块，`main.rs` 只负责注册和生命周期接线。
- [ ] 每次拆分先证明行为等价，再叠加功能改动。
- [ ] 禁止把全仓格式化、大规模重命名和功能实现放在同一补丁。
