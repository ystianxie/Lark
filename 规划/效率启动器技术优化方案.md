# Lark 效率启动器技术优化方案

> 目标：基于《效率启动器竞品对比与架构方案深度研究报告》，整理适合 Lark 当前阶段的技术优化方向，在不推翻现有 Tauri 2 + React + Rust 架构的前提下，提高搜索响应、结果质量、插件稳定性、索引可靠性和可诊断性。
>
> 适用范围：Windows 优先的 Lark 桌面启动器。
>
> 方案日期：2026-09-28
>
> 当前状态：规划完成，尚未授权实施；具体任务见 [效率启动器技术优化-TODO.md](效率启动器技术优化-TODO.md)。

## 1. 关键结论

竞品报告适合作为技术原则参考，但不应直接作为 Lark 的重构蓝图。

Lark 当前已经具备：

- Tauri 2 原生壳、窗口、托盘、快捷键和 IPC；
- React/WebView UI；
- Rust 搜索、SQLite、文件索引、剪贴板和 Windows 系统集成；
- JS/Python 插件运行能力；
- 文件全量重建、generation/staging、运行时 watcher 增量更新和异常状态管理。

因此推荐保留以下主干：

```text
Tauri 原生生命周期与系统集成
              ↓
React 搜索界面与结果编排
              ↓
Tauri Command / Event
              ↓
Rust 搜索、索引、排序、数据库与 Windows 能力
              ↓
受约束的 JS / Python 插件执行单元
```

不推荐改成“WPF 原生壳 + React + Node 常驻后端 + Rust 核心”。该方案会重复 Tauri 已承担的职责，增加进程管理、IPC、打包、内存和故障恢复成本，当前没有足够收益证明其必要性。

## 2. 关键假设

1. Lark 近期继续以 Windows 为首要平台，不为跨平台一致性牺牲 Windows 集成能力。
2. 当前目标是优化搜索、插件、索引和可靠性，不是立即建设插件商店或 AI 平台。
3. 第三方插件未来可能包含不完全可信代码，因此权限声明不能长期代替执行隔离。
4. 文件索引可能增长至数十万或更多记录，需要用实测决定是否引入 USN Journal 或 FTS5。
5. 已有文件 watcher 和全量重建路径是继续演进的基础，不另建平行索引系统。

| 优先级 | 方案 | 主要收益 | 复杂度 | 推荐阶段 |
| --- | --- | --- | --- | --- |

| P0 | 快速/后台 Provider 分流 | 慢插件不阻塞首屏 | 中 | 第一阶段 |
| P0 | 插件信任边界和超时 | 降低插件拖死或污染宿主风险 | 中高 | 第二阶段 |

| P1 | 用户选择历史排序 | 常用结果更稳定靠前 | 中 | 第二阶段 |

## 4. 方案一：统一搜索会话

### 4.1 当前问题

现有 `src/pluginExecution.js` 已实现同一执行键只保留最新待运行任务，但已经进入 `await execute()` 的旧任务无法被真正取消。随着本地搜索、插件、Python、网络和未来 AI 数据源增加，可能出现：

- 用户已经输入新关键词，旧查询仍消耗资源；
- 旧查询比新查询更晚返回并污染结果；
- 所有 Provider 被迫使用同一个等待节奏；
- 后台结果到达后抢占当前选中项；
- 无法统计一次查询中各数据源的实际耗时。

### 4.2 推荐模型

每次输入创建独立搜索会话：

```ts
interface SearchSession {
  queryId: number;
  query: string;
  startedAt: number;
  abortController: AbortController;
}
```

约束如下：

1. `queryId` 单调递增；
2. 新查询创建时取消上一会话；
3. Provider 结果必须携带 `queryId`；
4. UI 丢弃非当前 `queryId` 的返回；
5. 不支持物理取消的 Rust/外部进程任务也必须支持逻辑过期；
6. 用户手动移动选择后，后台结果不能改变当前选中项。

### 4.3 验收标准

- 快速连续输入时，界面只显示最后一次查询的结果；
- 已过期 Provider 的返回不会覆盖新结果；
- 查询失败或取消不会影响其他 Provider；
- 用户选择位置不会因后台结果插入而跳到其他项目；
- 可以从日志或诊断信息定位每个 Provider 的查询耗时。

## 5. 方案二：快速和后台 Provider 分流

### 5.1 Provider 分类

快速 Provider：

- 应用索引；
- 文件精确、标题前缀；
- 内置命令；
- 计算器；
- 文本片段；
- 剪贴板近期记录。

后台 Provider：

- 文件标题包含和路径包含；
- Python 插件；
- 网络插件；
- 外部程序状态查询；
- AI 或语义搜索。

### 5.2 推荐接口

```ts
interface SearchProvider {
  id: string;
  mode: "immediate" | "background";
  priority: number;
  search(context: SearchContext): Promise<SearchResult[]>;
}
```

可进一步为插件提供双接口：

```ts
queryImmediate?(context): SearchResult[];
queryBackground?(context, signal): Promise<SearchResult[]>;
```

快速接口不得启动 Python、遍历文件系统或访问网络。超过预算的插件记录诊断信息，并在达到明确阈值后降级为后台 Provider，而不是阻塞整个结果列表。

### 5.3 初始延迟预算

以下数值仅作为首轮实测基线，不是未经验证的产品承诺：

| 阶段 | 初始目标 |
| --- | --- |
| 本地首批结果 | 输入后 50ms 内 |
| 普通本地结果稳定 | 输入后 120ms 内 |
| 普通插件合并 | 输入后 150ms 内 |
| 后台结果开始展示 | 输入后 500ms 内 |

## 6. 方案三：统一结果模型与排序器

### 6.1 原则

现有文件查询的“精确 → 前缀 → 标题包含 → 路径包含”分层应保留。统一排序器不是用一种模糊算法替换所有查询，而是把各数据源结果转换为可比较的宿主模型。

```ts
interface SearchResult {
  id: string;
  providerId: string;
  type: "app" | "file" | "command" | "snippet" | "clipboard" | "plugin";
  title: string;
  subtitle?: string;
  matchKind: "exact" | "prefix" | "pinyin" | "token" | "substring" | "fuzzy";
  matchScore: number;
  sourcePriority: number;
  launchCount?: number;
  lastUsedAt?: number;
  actions: ResultAction[];
}
```

插件不直接决定跨 Provider 的最终总分，只返回标准化匹配信息。宿主统一组合：

```text
匹配质量
+ 数据源基础权重
+ 用户选择频率
+ 最近使用衰减
+ 固定/收藏权重
+ 当前上下文权重
- 不稳定结果惩罚
```

### 6.2 推荐匹配顺序

```text
精确标题
> 标题前缀
> 拼音/简拼前缀
> 标题词匹配
> 标题包含
> 路径包含
> 模糊匹配
```

### 6.3 用户选择学习

记录聚合信息而不是无限保存原始事件：

```text
normalized_query
result_identity
provider_id
select_count
last_selected_at
```

需要防止历史权重永久压制新安装应用，建议使用时间衰减，并提供清除学习记录的能力。

## 7. 方案四：插件运行时信任边界

### 7.1 当前风险

当前 JS 插件源码通过 Blob URL 动态 `import()` 到主 WebView，同宿主 React 页面处于同一 JavaScript Realm。Manifest 权限只控制宿主主动提供的 API，不能阻止插件访问 `window`、`document`、DOM、浏览器网络 API 或其他前端全局状态。

因此当前权限更适合作为“能力声明”，不能当作完整安全沙箱。

### 7.2 推荐两级运行时

#### 一级：受信任 UI 插件

- 仅允许 Lark 内置或经过审核的插件；
- 可以暂时保留当前 React/WebView 模式；
- 明确标记为可信代码，不对普通第三方开放。

#### 二级：普通第三方插件

- 查询逻辑优先运行在 Web Worker；
- Python、网络和长任务运行在独立 Sidecar/子进程；
- 插件不能直接操作主页面 DOM；
- 插件返回结构化 `SearchResult`、`Action` 或声明式 `ViewSchema`；
- 宿主负责渲染、权限检查、超时和取消。

### 7.3 不推荐的做法

- 不因为插件需要 JS 就增加 Node 常驻主后端；
- 不承诺 Web Worker 是完整操作系统安全沙箱；
- 不允许普通第三方插件直接获得任意 Tauri `invoke` 能力；
- 不在权限、超时、API 版本未稳定前建设公开插件商店。

## 8. 方案五：文件索引可靠性与 USN 评估

### 8.1 与现有计划的关系

现有 `规划/文件系统监听-三阶段实施计划.md` 和 `规划/文件系统监听-未完成TODO.md` 是文件 watcher 与增量 SQLite 更新的权威实施文档。本方案不复制或替代其中任务。

当前优先完成已有计划中的：

- watcher 异常恢复；
- stale 状态处理；
- 配置与索引状态校验；
- 事件积压、批处理耗时和重建次数统计；
- Windows 实机验证和大规模文件变更测试。

### 8.2 USN Journal 的正确定位

只有在基准测试证明现有 watcher 在大规模变化、应用离线期间变化捕获或恢复速度上不满足要求时，再增加 USN Journal。

推荐结构：

```text
全量扫描成功提交 ──> 建立可靠基线
                           │
Watcher 事件 ──> debounce ──> 唤醒增量读取
                           │
                USN Journal 持久变化记录
                           │
     Journal 缺失/游标过期/卷变化 ──> 回退全量扫描
```

Watcher 是低延迟信号，USN 是可恢复的增量来源，两者不应独立双写数据库。

每卷至少保存：

```text
volume_serial_number
journal_id
last_usn
last_successful_scan_at
index_schema_version
```

必须处理 NTFS 之外文件系统、移动磁盘、Journal 重建、游标过期和目录重命名等边界。

## 9. 方案六：性能预算与可观测性

### 9.1 需要采集的指标

窗口：

- 热键按下到窗口可见；
- 窗口可见到输入框可操作；
- 首次打开和后续打开分别统计。

搜索：

- 输入到首批结果；
- 输入到稳定结果；
- 每个 Provider 耗时；
- 取消和过期结果数量；
- 结果列表重排次数。

索引：

- 全量扫描耗时和文件数量；
- watcher 事件积压量；
- 单批处理数量和事务耗时；
- stale 次数和全量重建次数。

插件：

- 激活耗时；
- 查询耗时；
- 超时、取消和崩溃次数；
- Python/Sidecar 启动和执行耗时。

### 9.2 数据边界

- 默认只记录本地技术指标，不记录用户查询原文；
- 查询长度、结果数量等可以聚合记录；
- 诊断导出前应明确字段，避免意外包含剪贴板、文件名或插件配置；
- 指标采集本身不能明显增加输入延迟。

## 10. 方案七：触碰式模块拆分

以下文件体积较大，后续修改风险较高：

- `src-tauri/src/api/explorer.rs`；
- `src/panels/settingComponent.jsx`；
- `src-tauri/src/main.rs`；
- `src-tauri/src/utils/database.rs`；
- `src/App.jsx`。

不进行一次性全面重构。每次实施相关功能时，只拆分被修改领域的完整职责：

```text
search/
  coordinator
  provider
  ranking
  result

index/
  app_index
  file_index
  full_scan
  incremental

settings/
  hotkeys
  indexes
  plugins
  clipboard
```

拆分必须保持行为不变，并在同一阶段完成结构验证；不能把整理代码与功能改动混成无法审查的大补丁。

## 11. 延后或不实施的方案

当前不实施：

- WPF/Swift 双原生壳重写；
- Node 常驻业务后端；
- 立即建设插件商店；
- 用 BM25/FTS5 替换现有精确和前缀搜索；
- 未经基准验证直接引入 Trie、向量数据库或语义搜索；
- 在统一动作、权限和插件隔离稳定前接入可执行系统操作的 AI；
- 为追求形式上的跨平台统一而移除 Windows 专有能力。

FTS5 仅在“多词、描述或长文本查询”基准证明有收益后作为补充层。AI 应建立在受权限控制的统一 Action 模型上，不能直接获得任意系统能力。

## 12. 分阶段路线

### 第一阶段：搜索链路稳定化

- 搜索会话、`queryId` 和过期结果治理；
- 快速/后台 Provider；
- 选中项稳定规则；
- 基础耗时指标和诊断日志；
- 不改变现有搜索算法和数据库结构。

### 第二阶段：排序和插件约束

- 统一 `SearchResult`；
- 宿主统一排序；
- 用户选择历史；
- 插件超时和自动降级；
- Worker 查询运行时原型；
- 可信插件和普通插件分级。

### 第三阶段：索引可靠性

- 完成已有文件 watcher 计划中的异常恢复和实机测试；
- 建立索引状态诊断；
- 用大规模测试决定是否引入 USN；
- 如需 USN，先做独立技术验证，不直接替换现有 watcher。

### 第四阶段：生态和智能能力

- 稳定插件 API 版本；
- 声明式 UI/Action 协议；
- Sidecar 生命周期和资源限制；
- 插件来源、签名和升级策略；
- 最后评估插件商店和 AI 动作编排。

## 13. 总体验收标准

- 快速输入不会出现旧结果覆盖新结果；
- 慢插件和网络任务不会阻塞本地首批结果；
- 后台结果加入时不会抢占用户当前选择；
- 所有 Provider 都可以定位耗时、失败、取消和超时；
- 插件权限声明与实际执行边界一致，不以同 Realm API 隐藏冒充安全隔离；
- 文件索引异常后存在明确的 stale、恢复或全量重建路径；
- 性能目标由 Lark 实测数据决定，不直接照搬竞品宣传数字；
- 新方案复用现有 Tauri、Rust、SQLite、配置和索引路径，不新增没有必要的平行机制。
