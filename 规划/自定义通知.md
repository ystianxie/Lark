# 自定义通知设计方案

> 目标：在 Lark 中提供统一的应用内通知能力。业务代码只负责提交通知内容，Rust 负责状态、窗口生命周期、Action 和屏幕定位，React 负责 UI 与动画。
>
> 设计结论：使用一个独立的 Tauri 通知窗口，在窗口内部堆叠多条通知；窗口尺寸根据前端实际内容动态调整；窗口显示在目标屏幕右上角。

## 1. 总体架构

```text
业务前端 notify.success()/info()/warning()/error()
                 │ invoke
                 ▼
Rust NotificationManager（权威状态）
  ├─ 通知列表、生命周期、enabled/paused
  ├─ 创建、显示、隐藏 notification 窗口
  ├─ 屏幕选择与右上角定位
  └─ 白名单 Action 执行
                 │ emit notification-state
                 ▼
React 通知页面：列表、动画、按钮和尺寸测量
```

固定窗口 label：`skylark` 为主窗口，`notification` 为通知窗口。不为每条通知创建独立窗口，所有通知在一个 WebView 中纵向堆叠。

## 2. 核心行为

### 2.0 已确认产品决策

- 暂停期间丢弃 `success/info`，保留 `warning/error`；恢复后重新按完整时长计时，不保存暂停前剩余时间。
- 默认同时完整展示最多 3 条；其余通知保留为卡片层叠，只露出一小行。
- 默认时长：`success/info` 5 秒，`warning` 8 秒，`error` 不自动关闭。
- 队列最多保留 20 条；超限时优先丢弃最旧的 `success/info`，极端情况下再淘汰最旧项。
- 新通知始终插入顶部；展开状态下新通知仍插入顶部，不自动折叠或滚动。
- 点击层叠区域可展开，展开状态保持；再次点击层叠区域或空白区域折叠。
- 折叠最大高度为工作区高度 40%，不超过 520 logical px；展开最大高度为工作区高度 70%，不超过 800 logical px。展开上限保留为可调配置。
- 窗口宽度默认 380 logical px，小屏幕按工作区宽度和安全边距缩小。
- 右上角边距为顶部 16、右侧 16 logical px。
- 悬停会暂停 `success/info/warning` 倒计时，移开后继续；`error` 始终手动关闭。
- 卡片空白区域不执行操作；Action 成功后关闭当前通知，失败则保留并显示错误状态。
- 首期不做重复通知合并。
- 标题最多 2 行、消息最多 4 行；支持单条消息展开，但仍受窗口高度限制。

### 2.1 通知窗口

- 只有一个实例；没有可显示通知时隐藏而不是销毁。
- 首次产生通知时按需创建。
- 无边框、跳过任务栏、置顶、不主动抢焦点。
- 可接收鼠标事件，Action 按钮不能鼠标穿透。
- 应用退出时由 Tauri 回收。

### 2.2 内容驱动的窗口尺寸

参考主窗口已有的“根据内容调整大小”思路，但尺寸必须来自通知页面的实际布局：

```text
通知列表变化 -> React 完成布局 -> ResizeObserver 测量容器
-> emit resize-request(width, height) -> Rust 校验边界并 set_size()
-> 重新定位到目标屏幕右上角
```

- 宽度固定或限制在小范围内，避免长文本横向扩张。
- 高度按实际内容动态变化，并设置最大高度。
- 用 `ResizeObserver` 和短时间合并避免高频 `set_size`。
- DPI 或显示器变化后重新测量和定位。
- 不使用“通知条数 × 固定高度”估算。

### 2.3 暂停语义

暂停只影响通知窗口是否显示：`pause()` 隐藏窗口，暂停期间不显示通知，业务 API 不需要额外处理；`resume()` 按约定策略恢复。

暂停期间丢弃 `success/info`，保留 `warning/error`。恢复时保留的 `warning` 重新按完整 8 秒计时，不保存暂停前剩余时间；`error` 仍需手动关闭。`enabled=false` 与 `paused=true` 保持区分：前者是全局关闭，后者是临时隐藏。

## 3. 前端 API

```ts
notify.success({
  title: "下载完成",
  message: "Rust-1.90.0.zip",
  actions: [actions.open(filePath), actions.openDir(filePath)],
});
```

```ts
type NotificationLevel = "success" | "info" | "warning" | "error";
type NotificationAction =
  | { type: "open"; path: string; label?: string }
  | { type: "open_dir"; path: string; label?: string }
  | { type: "close"; label?: string };
type NotificationOptions = {
  title: string;
  message?: string;
  actions?: NotificationAction[];
  durationMs?: number;
};
```

提供 `notify.success/info/warning/error` 和 `actions.open/openDir/close`。前端只传受支持的数据，不传函数、任意事件名或可执行代码。

## 4. Rust NotificationManager

建议新增：

```text
src-tauri/src/notification/
├── mod.rs
├── model.rs
├── manager.rs
└── action.rs
```

Manager 负责生成 ID、保存列表、自动过期、关闭、`enabled/paused`、窗口创建与显示隐藏、状态事件和尺寸定位。

建议 command：`notify`、`dismiss_notification`、`invoke_notification_action`、`get_notifications`、`set_notifications_enabled`、`set_notifications_paused`。

建议事件：`notification-state`、`notification-window-resize`。窗口刷新或重新创建时必须通过 `get_notifications` 同步，不能依赖一次性事件不丢失。

## 5. Action 安全边界

Action 是数据，不是前端函数。Rust 只执行 `OpenFile`、`OpenDirectory`、`Close` 等白名单 Action。

执行前校验路径非空并 canonicalize，检查目标存在性及文件/目录类型；复用项目已有的 `open_file`、`open_explorer` 能力，并将启动失败转成可读错误。拒绝任意 Shell 命令、任意协议和未声明 Action。插件调用通知时也必须遵守同一白名单。

## 6. 多屏与右上角定位

优先使用主窗口所在显示器；主窗口不可见或不存在时退回主显示器；显示器、DPI 或窗口尺寸变化后重新定位。

使用排除任务栏的工作区坐标：

```text
x = workArea.right - notificationWidth - marginRight
y = workArea.top + marginTop
```

显示器工作区及窗口位置采用物理像素；WebView 上报的尺寸采用逻辑像素。定位时按目标显示器的 scale factor 将通知宽高和边距转换为物理像素，不能直接把 Windows 原生坐标当 CSS 像素。主窗口移动、尺寸或 DPI 变化以及通知窗口尺寸变化后重新定位。边距、最大宽高集中在通知窗口配置中。

## 7. 分阶段实施

### 第一阶段：MVP

- 单通知窗口和 React 通知列表。
- 四种通知等级、自动关闭、手动关闭。
- `open`、`open_dir`、`close`。
- 内容驱动高度、主窗口所在屏幕右上角定位。
- 暂停隐藏窗口，Rust 状态可重新同步。

### 第二阶段：稳定版

- 多显示器和 DPI 实机验证。
- ResizeObserver 防抖、窗口尺寸边界、通知过多时的队列/淘汰。
- 主窗口隐藏、销毁、重建时的生命周期处理。
- Action 错误展示、日志、暗色模式和无障碍细节。
- 完善展开卡片的视觉层级和可调高度参数。

### 第三阶段：增强版（由实际需求触发，不属于首期）

- 通知历史及其持久化（仅在需要回看已消失通知时）。
- 通知来源标识与筛选；插件 `notification.send` 权限本身已在当前实现中提供。
- 用户可配置的通知行为持久化（仅在需要设置界面时）。
- 复杂 Action 与 macOS 等跨平台窗口视觉/行为适配。

## 8. 非目标

首期不做 Windows 原生 Toast、egui、每条通知一个窗口、前端可执行函数、固定条高计算、通知历史持久化和跨进程同步。

## 9. 插件与 Python 使用边界

通知能力按任务生命周期划分，不把通知窗口对象暴露给 Python，也不让 Python 直接调用 Tauri API。

### 9.1 Panel 插件

Panel 有当前页面上下文，默认优先使用 Panel 内的 loading、进度、成功和错误提示。只有在 Panel 已关闭、用户切换到其他页面，或结果需要跨页面提醒时，才使用全局通知。

JS 插件可通过宿主提供的统一接口调用通知，例如 `context.ui.notify(...)`；插件不得直接调用 Tauri `invoke` 或操作宿主全局 DOM。

### 9.2 普通 action/python workflow

当前 `action/python` 是前台请求-响应模型：

```text
调用 workflow -> 启动 Python -> 等待单个 JSON 结果 -> Python 进程结束
```

它适合查询、转换、格式化和短时文件处理。Python 不直接发起通知；可以在最终 JSON 结果中携带可选的结构化通知描述，由 JS runtime 和宿主统一校验后决定是否展示：

```json
{
  "ok": true,
  "result": {"data": "..."},
  "notification": {
    "level": "success",
    "title": "处理完成",
    "message": "已处理 128 个文件"
  }
}
```

Panel 仍存在时优先使用 Panel 内反馈；Panel 已关闭或结果需要跨页面提醒时才转成全局通知。当前普通一次性 Python workflow 可在成功 JSON 中返回顶层 `notification`；宿主只在 workflow 结束后校验并转发。interactive workflow/Panel 不触发全局通知。`notification` 只能使用通知白名单字段和 Action，不能传函数、任意事件名或 Shell 命令。

当前实现边界：Panel 活跃期间只展示 Panel 自己的 loading、进度、成功和错误状态，避免同一结果重复弹出全局通知。普通一次性 action/python workflow 的最终结果未来接入 `notification` 字段时，由宿主在 workflow 完成后统一校验并决定是否转为全局通知；Python 代码本身不获得 Tauri 调用能力。

### 9.3 当前不支持后台 Python

当前插件生命周期没有正式的后台任务能力。`run_python_plugin` 是一次性 stdin/stdout JSON 协议，默认等待进程结束；Panel 卸载也不会把任务转移到后台。已经启动的进程可能继续运行，但这不应被视为可依赖的产品行为。

因此首期不允许 Python 中途主动推送通知，也不为普通 Python 调用引入流式协议。短时任务的反馈通过最终结果承载；Panel 任务的反馈在 Panel 内完成。

### 9.4 未来后台任务模型

只有在确实需要下载、批量处理、扫描、索引等长任务时，才新增独立的后台任务 API，而不是隐式扩展 `runPython`：

```text
start job -> jobId -> progress/log/notification -> completed/failed/cancelled
```

届时再设计后台进程托管、取消、状态查询、任务完成通知和可选 NDJSON 流式协议。进度条通知只适合这些长任务，不适合普通短时脚本。

## 10. 验收补充

- Panel 插件默认可以在页面内反馈，不强制使用全局通知。
- 普通 Python 只能通过最终结果携带可选通知，不能直接操作通知窗口。
- Panel 关闭后，普通 Python 不承诺继续执行、通知或结果投递。
- 未实现后台任务 API 前，不承诺 Python 中途通知、进度流和任务取消。

## 9. 验收标准

- 连续发送多条通知时只创建一个窗口。
- 内容换行、按钮数量变化后窗口高度跟随实际内容。
- 通知显示在目标显示器右上角并避开任务栏。
- 主窗口在不同显示器时，通知跟随主窗口所在显示器。
- 暂停后窗口立即隐藏，暂停期间没有可见通知。
- Action 由 Rust 执行，非法路径不会导致崩溃。
- 通知窗口刷新或重建后仍能从 Rust 恢复当前状态。
- 通知窗口不会抢焦点、阻塞主窗口或出现在任务栏。
