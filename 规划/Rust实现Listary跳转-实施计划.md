# Rust 实现 Listary 跳转：可执行实施计划

> 基于：[Rust实现Listary跳转.md](./Rust实现Listary跳转.md)  
> 计划日期：2026-09-17  
> 目标项目：Lark（Tauri 2 + Rust，Windows 优先）

## 1. 计划目标

在 Lark 中实现一个 Windows 专属的“Listary 风格目录跳转”能力：

1. 用户先在 Windows Explorer 中访问一个目录；
2. Lark 记住最近一次有效的 Explorer 目录；
3. 当文件打开/保存对话框位于前台时，用户按下 `Ctrl+G`；
4. Lark 将该文件对话框导航到记录的 Explorer 目录；
5. 如果当前环境不满足条件，快捷键应尽量不破坏原应用行为，并给出可诊断的失败原因。

本计划只覆盖上述核心闭环，不在第一版实现目录搜索、固定目录、历史列表、双击 Ctrl、DLL 注入或完整 Listary 替代品。

---

## 2. 关键假设

实施前必须明确以下假设；其中任一项不成立，都需要调整方案：

1. **首期仅支持 Windows 10/11**，macOS 和 Linux 不实现此功能。
2. Lark 是长期驻留的 Tauri 进程，可在后台维护 Explorer 路径状态和键盘监听线程。
3. 第一版主要支持 Windows 标准的打开/保存对话框，以及结构接近标准对话框的 Chromium/Electron 对话框。
4. 目标路径只接受本机可访问的文件系统目录；虚拟 Shell 路径（如“此电脑”“快速访问”）首期可以识别，但不保证可跳转。
5. `Ctrl+G` 是否覆盖应用原有快捷键必须可配置；默认只在已确认的文件对话框中拦截。
6. 当前项目已经依赖 `windows = 0.58`、`winapi`、`rdev` 和 Tauri 全局快捷键插件，但实施时应避免同时用多套 API 表达相同能力。

## 3. 对原方案的对抗式审查

### 3.1 `IFileDialog::SetFolder` 不能作为外部进程的通用主路径

原方案把 `IFileDialog::SetFolder` 作为优先导航方式，但 Lark 是文件对话框所属应用之外的进程。通常不能仅凭对话框 `HWND` 获取另一个进程内部的 `IFileDialog` COM 实例。

因此：

- `IFileDialog::SetFolder` 适合 Lark 自己创建并持有的对话框；
- 若要控制其他进程的对话框，通常需要进程内注入、目标应用协作或其它高复杂度机制；
- MVP 不应依赖这一假设，否则会在架构上走入死路。

**结论：MVP 主路径采用 UI Automation；必要时使用受控的键盘输入作为降级方案。暂不做 DLL 注入。**

### 3.2 不能只按窗口类名判断文件对话框

仅判断 `#32770` 会产生误判，因为大量普通 Win32 对话框也使用这个类名；现代应用的文件对话框也未必完全符合这一结构。

应组合使用：

- 前台窗口及其根窗口；
- 窗口所属进程；
- UI Automation 控件树特征；
- 地址栏、文件名框、打开/保存按钮等关键控件；
- 可选的窗口类名和标题作为辅助证据。

检测结果应区分 `Confirmed`、`Probable`、`NotDialog`，只有 `Confirmed` 默认允许吞掉快捷键。

### 3.3 不能在低级键盘 Hook 回调里执行 COM/UIA 操作

`WH_KEYBOARD_LL` 回调必须快速返回。若直接在回调中枚举窗口、调用 COM 或等待 UI Automation，可能造成输入卡顿，甚至被 Windows 移除 Hook。

正确结构是：

```text
Hook 回调
  -> 只记录按键并投递 JumpRequest
  -> 工作线程读取请求
  -> 检测对话框
  -> 执行导航
```

是否吞掉 `Ctrl+G` 必须在 Hook 回调可承受的时间内，根据已缓存的前台窗口分类决定。

### 3.4 `RegisterHotKey` 简单，但不适合作为最终实现

项目已有 `tauri-plugin-global-shortcut`，可以快速验证快捷键到业务逻辑的链路，但注册 `Ctrl+G` 后会全局占用该组合键，无法在非文件对话框中自然透传。

所以：

- 可以将 Tauri 全局快捷键用于开发期 Spike；
- 正式版本推荐 Windows 专属 `WH_KEYBOARD_LL`；
- 不应长期同时保留两套快捷键监听实现。

### 3.5 Explorer 路径不能只依赖窗口标题或地址栏文本

窗口标题可能只包含文件夹名，地址栏文本又会受语言、显示模式和 Windows 版本影响。主路径应使用 Shell COM 的 `IShellWindows`/Explorer `LocationURL`，并正确处理 URL 解码、网络路径和失效窗口。

## 4. 推荐架构

采用“小核心 + Windows 平台适配层”，先放在现有 `src-tauri` 中，不创建独立 workspace，也不做不必要的跨平台抽象。

```text
src-tauri/src/
├── listary_jump/
│   ├── mod.rs                 # 生命周期、统一入口、公共类型
│   ├── state.rs               # 最近 Explorer 目录和前台窗口分类缓存
│   └── windows/
│       ├── mod.rs
│       ├── explorer.rs        # Shell COM 获取 Explorer 目录
│       ├── dialog.rs          # 文件对话框识别
│       ├── navigator.rs       # UIA 导航与降级策略
│       ├── keyboard_hook.rs   # WH_KEYBOARD_LL、事件投递
│       └── worker.rs          # 后台工作线程和请求串行化
└── main.rs                    # setup/exit 中启动和停止服务
```

核心类型保持精简：

```rust
struct ExplorerLocation {
    hwnd: isize,
    path: PathBuf,
    observed_at: Instant,
}

enum DialogConfidence {
    Confirmed,
    Probable,
    NotDialog,
}

struct JumpRequest {
    foreground_hwnd: isize,
    requested_at: Instant,
}

enum JumpOutcome {
    Success,
    NoRecentExplorerPath,
    PathUnavailable,
    UnsupportedDialog,
    NavigationFailed,
}
```

不建议首期设计公开的多实现 `DialogNavigator` 插件体系。当前只有 UIA 主实现和一个内部降级策略，直接使用普通函数或私有枚举更简单；等确实出现第三种稳定导航机制时再抽象 trait。

## 5. 导航策略

推荐按以下顺序执行：

### 主路径：UI Automation

1. 获取触发时的前台根窗口；
2. 再次确认它仍是同一个窗口，避免用户切换窗口后误操作；
3. 在 UIA 树中查找地址栏或可编辑路径控件；
4. 优先使用 `ValuePattern::SetValue`；
5. 若控件拒绝直接赋值，则聚焦控件后发送受控输入；
6. 提交路径；
7. 在限定时间内验证对话框的当前目录或控件状态发生预期变化。

### 降级路径：键盘导航

仅对经过适配和验证的对话框启用：

```text
Ctrl+L 或 Alt+D
  -> 写入路径
  -> Enter
```

该方法依赖应用快捷键和焦点行为，不能作为所有应用的通用保证。必须维护应用/对话框兼容性测试表，失败时不得盲目连续发送按键。

### 暂不采用

- 跨进程直接调用 `IFileDialog::SetFolder`；
- DLL 注入；
- 按固定坐标点击；
- 依赖某个语言版本的窗口标题；
- 无条件模拟大量按键。

## 6. 分阶段实施步骤

## 阶段 0：建立可重复的验证基线

**目的：** 在动核心代码前明确支持范围和验证方法。

### 任务

- [ ] 确认最低 Windows 版本及测试机器：至少 Windows 10、Windows 11 各一套。
- [ ] 建立手工测试应用清单：记事本、Paint、Office（若可用）、Chrome/Edge、VS Code、一个传统 Win32 应用。
- [ ] 为每个应用分别测试“打开”和“另存为”。
- [ ] 确定默认热键冲突策略：建议默认只在 `Confirmed` 文件对话框中拦截。
- [ ] 确定日志位置和日志级别；日志不得记录用户输入的文件名等不必要隐私信息。

### 交付物

- 一张兼容性测试表；
- 明确的 MVP 支持边界；
- 可复现的手工测试步骤。

### 完成标准

团队能够一致回答“哪些对话框必须支持、哪些暂不支持、如何判断成功”。

---

## 阶段 1：Explorer 路径探针（独立 Spike）

**目的：** 先验证最核心且相对独立的输入数据源。

### 任务

- [ ] 补齐 `windows` crate 所需 feature，至少覆盖 COM、Shell、Foundation 和 Variant 相关 API。
- [ ] 在专用线程调用 `CoInitializeEx`，明确线程使用 STA 还是 MTA；Shell/UIA 的 COM 对象不得跨未封送线程传递。
- [ ] 使用 `IShellWindows` 枚举 Explorer 窗口。
- [ ] 提取 Explorer `HWND` 和 `LocationURL`。
- [ ] 将 `file:///C:/...` 正确转换为 Windows 路径，处理空格、中文、`%xx` 编码和 UNC 路径。
- [ ] 过滤非文件系统位置，记录可诊断原因。
- [ ] 建立“最近有效 Explorer 目录”缓存；路径不存在时不得覆盖最后一个有效值。
- [ ] 加入纯函数单元测试：URL 解码、盘符路径、UNC、虚拟路径、失效路径。

### 建议实现方式

先采用低频轮询（例如 300～500 ms）枚举 ShellWindows，而不是立即引入复杂事件订阅。MVP 中窗口数量通常很少，轮询更容易验证和恢复。

### 完成标准

在多个 Explorer 窗口间切换、进入中文目录、UNC 目录和关闭窗口时，日志中的最近有效路径与用户实际选择一致，且后台 CPU 占用可接受。

---

## 阶段 2：文件对话框识别探针

**目的：** 在拦截快捷键前，证明能够可靠区分目标对话框与普通窗口。

### 任务

- [ ] 获取前台窗口并规范化为根窗口/所有者窗口。
- [ ] 采集窗口类名、进程名、控件树关键特征。
- [ ] 用 UI Automation 查找地址栏、文件名输入框、打开/保存按钮等特征。
- [ ] 输出 `Confirmed`、`Probable`、`NotDialog` 和判定原因。
- [ ] 对测试清单逐项记录检测结果。
- [ ] 确保密码框、浏览器页面普通输入框、IDE 编辑器等不会被判为文件对话框。

### 完成标准

MVP 测试清单中的目标对话框均达到 `Confirmed` 或有明确的应用级适配理由；普通窗口没有会导致快捷键被吞掉的误判。

---

## 阶段 3：单次 UIA 导航

**目的：** 不接入全局键盘 Hook，先通过测试命令完成一次可验证跳转。

### 任务

- [ ] 增加仅开发构建可用的 Tauri command 或调试入口，例如 `debug_jump_dialog(path)`。
- [ ] 定位对话框路径控件，优先调用 ValuePattern。
- [ ] 实现单次、受控的聚焦和提交操作。
- [ ] 设置总超时，建议单次操作不超过 1～2 秒。
- [ ] 导航前验证目录存在且为目录。
- [ ] 导航后进行可观察验证；无法验证时返回“结果未知”，不能直接报告成功。
- [ ] 对权限不同的目标进程进行测试，确认完整性级别限制的表现。

### 完成标准

不依赖全局快捷键，调试入口可让支持清单中的文件对话框跳到指定目录，并返回结构化结果。

---

## 阶段 4：服务状态与请求工作线程

**目的：** 把路径跟踪、窗口检测和导航串成线程安全的后端服务。

### 任务

- [ ] 实现 `ListaryJumpService` 生命周期：`start`、`stop`、异常恢复。
- [ ] 使用有界 channel 投递 `JumpRequest`，防止按键连发积压。
- [ ] 同一时刻只允许一个导航任务执行；重复请求进行合并或丢弃。
- [ ] 将最近路径与窗口分类缓存放入清晰的共享状态中，避免全局可变裸指针。
- [ ] 在 Tauri `setup` 中启动，在退出事件中清理 Hook、线程和 COM。
- [ ] 用结构化日志记录阶段、耗时和失败分类。

### 完成标准

连续触发、快速切换窗口、退出 Lark 和目标应用崩溃时，不死锁、不泄漏后台线程、不持续占用输入。

---

## 阶段 5：接入 `WH_KEYBOARD_LL`

**目的：** 实现只在正确上下文中生效的 `Ctrl+G`。

### 任务

- [ ] 在独立线程安装 Hook 并运行 Windows 消息循环。
- [ ] 正确处理左右 Ctrl、按键按下/释放、自动重复和注入事件。
- [ ] Hook 回调只做常量时间判断和消息投递，禁止执行 COM/UIA/磁盘 IO。
- [ ] 只有缓存状态为 `Confirmed` 且请求成功投递时才吞掉 `Ctrl+G`。
- [ ] `Probable` 默认不吞按键；可通过开发配置观察行为。
- [ ] Lark 退出或服务关闭时调用 `UnhookWindowsHookEx`。
- [ ] 与现有 Tauri 全局快捷键注册逻辑隔离，避免重复注册 `Ctrl+G`。

### 完成标准

- 文件对话框中 `Ctrl+G` 能触发跳转；
- 浏览器、编辑器、终端等普通窗口中的 `Ctrl+G` 保持原行为；
- 长按、快速连按和切换窗口不会造成重复输入或卡顿；
- Hook 被移除或线程异常时不会影响系统键盘输入。

---

## 阶段 6：配置与最小用户反馈

**目的：** 让功能可关闭、可调整、可诊断，而不是写死在后台。

### 任务

- [ ] 添加 Windows 专属开关，默认值在内部测试后再决定。
- [ ] 添加可配置快捷键；修改时检测冲突并支持回滚到旧值。
- [ ] 提供“最近 Explorer 目录”和“上次跳转结果”的只读诊断信息。
- [ ] 对以下情况给出轻量反馈：无最近目录、路径失效、不支持的对话框、权限不足。
- [ ] 功能关闭时完全卸载 Hook，而不是仅在回调中忽略。

### 完成标准

用户可以不开启此功能；错误不会静默到无法排查；配置失败不会让快捷键永久失效。

---

## 阶段 7：回归、性能与发布门禁

### 自动化检查

- [ ] `cargo fmt --check`
- [ ] `cargo check`（Windows target）
- [ ] `cargo clippy --all-targets`，新增代码不得引入未解释的 warning。
- [ ] 路径解析、状态更新、请求去重和判定逻辑单元测试。
- [ ] 可抽离的窗口特征判定使用录制的轻量数据做表驱动测试。

### 手工回归

- [ ] Explorer：本地盘、中文、空格、UNC、窗口关闭、虚拟目录。
- [ ] 对话框：打开、另存为、文件夹选择。
- [ ] 应用：标准 Win32、Office、Chromium/Electron、至少一个不支持案例。
- [ ] 输入：普通 `Ctrl+G`、左右 Ctrl、长按、快速连按、输入法开启状态。
- [ ] 生命周期：启动、功能开关、睡眠唤醒、Explorer 重启、Lark 退出。
- [ ] 权限：普通 Lark 对普通应用；普通 Lark 对管理员应用应明确失败而非假成功。

### 发布门禁

以下任一条件成立则不能默认启用：

- 普通窗口中的 `Ctrl+G` 有可复现的误拦截；
- 导航可能把路径输入到非文件对话框；
- Hook 回调造成明显键盘延迟；
- 退出后 Hook 未可靠卸载；
- 失败被错误报告为成功。

## 7. 预计文件改动

第一版预计只改动以下区域：

| 文件/目录 | 变更 |
|---|---|
| `src-tauri/Cargo.toml` | 补充精确的 `windows` crate features；评估是否移除重复输入依赖 |
| `src-tauri/src/main.rs` | 注册服务生命周期和必要的调试命令 |
| `src-tauri/src/listary_jump/mod.rs` | 服务入口与公共结果类型 |
| `src-tauri/src/listary_jump/state.rs` | 最近路径、窗口分类和请求状态 |
| `src-tauri/src/listary_jump/windows/explorer.rs` | Explorer Shell COM 跟踪 |
| `src-tauri/src/listary_jump/windows/dialog.rs` | 文件对话框检测 |
| `src-tauri/src/listary_jump/windows/navigator.rs` | UIA 导航与验证 |
| `src-tauri/src/listary_jump/windows/keyboard_hook.rs` | 低级键盘 Hook |
| `src-tauri/src/listary_jump/windows/worker.rs` | 请求队列和后台执行 |
| 现有配置文件/前端设置页 | 仅在阶段 6 添加开关、快捷键和诊断信息 |

不要把该能力继续堆入现有超过千行的 `api/explorer.rs`；它当前主要承担搜索、索引和打开文件等职责，与 Windows Shell 窗口跟踪不是同一个变化原因。

## 8. 里程碑与依赖关系

```text
M0 验证基线
 ├─> M1 Explorer 路径探针
 └─> M2 对话框识别探针
       M1 + M2
          └─> M3 单次 UIA 导航
                 └─> M4 后台服务
                        └─> M5 条件式 Ctrl+G Hook
                               └─> M6 配置与反馈
                                      └─> M7 发布验证
```

关键路径是 **M2 → M3**。如果无法稳定识别并导航目标对话框，继续开发键盘 Hook 没有价值。

建议按可停止的 Spike 推进：M1、M2、M3 任一阶段失败，都先记录证据并重新评估，而不是用更危险的输入模拟或注入手段掩盖问题。

## 9. 风险清单与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 不同应用的对话框控件树差异大 | 部分应用无法跳转 | 建兼容性矩阵；主路径 UIA，按证据增加小型适配器 |
| 高权限目标进程限制 UIA/输入 | 无法控制管理员应用 | 明确支持边界；不默认要求 Lark 管理员运行 |
| `Ctrl+G` 与应用快捷键冲突 | 用户原行为被破坏 | 仅 Confirmed 时吞键；支持关闭和改键 |
| Hook 回调过慢 | 全系统输入卡顿 | 回调只投递消息；工作线程执行耗时操作 |
| Explorer 返回虚拟 Shell URL | 无法转换为文件路径 | 只缓存可验证的文件系统路径，保留失败原因 |
| 前台窗口在请求期间变化 | 路径输入到错误窗口 | 请求保存 HWND，执行前再次验证前台和窗口身份 |
| 模拟输入污染剪贴板 | 用户数据被覆盖 | 优先 ValuePattern；若必须用剪贴板，保存并条件恢复，首期最好避免 |
| 多套快捷键库并存 | 重复触发、难排查 | 正式实现只保留一个 Ctrl+G 入口 |
| Windows API crate 混用 | 类型转换和维护成本上升 | 新模块优先统一使用 `windows` crate；仅在现有接口边界使用 `winapi` |

---

## 10. MVP 验收标准

只有同时满足以下条件，才算 MVP 完成：

1. Lark 能持续记录最近一个有效的 Explorer 文件系统目录；
2. 在支持清单中的文件打开/保存对话框按 `Ctrl+G`，能跳到该目录；
3. 在普通应用窗口中按 `Ctrl+G`，原应用行为不被破坏；
4. 无 Explorer 路径、路径失效、对话框不支持、权限不足时均安全失败；
5. 连续触发不会并发执行多个导航任务；
6. Lark 退出或关闭功能后不再保留键盘 Hook；
7. 自动检查通过，兼容性矩阵中的必测项完成；
8. 日志能够区分“未检测到对话框”“没有有效路径”“UIA 操作失败”“验证失败”，不能只返回统一错误。

---

## 11. 明确不在 MVP 范围内

- DLL 注入或目标进程内 COM 调用；
- 完整复刻 Listary 搜索界面；
- 最近目录选择器、收藏夹和模糊搜索；
- 自动跟随 Explorer 焦点后立即跳转，不按快捷键；
- 对所有第三方自绘文件选择器作兼容承诺；
- 自动提权或要求 Lark 始终以管理员身份运行；
- 为该功能进行大规模 `main.rs` 或现有 API 的无关重构。

---

## 12. 推荐的第一轮工作包

第一轮只做三个可独立验证的 Spike，不接正式快捷键：

1. **Explorer Spike**：打印最近活动 Explorer 的可用文件系统路径；
2. **Dialog Detector Spike**：打印前台窗口是否为文件对话框及判定证据；
3. **Navigator Spike**：通过开发命令把指定文件对话框跳到给定路径。

完成这三项后再做一次技术复盘。如果 UIA 在目标应用集合中可靠，再进入服务化和 Hook；如果不可靠，基于失败样本决定是增加有限适配器、缩小支持范围，还是单独评估更高成本方案。

这是最小、可维护且能尽早证伪核心假设的推进顺序。
