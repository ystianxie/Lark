# 插件返回值与通知处理流程

本文记录 Lark 当前插件运行时对返回值和通知的包装、拆包及显示流程，适用于 `action` 和 `python` workflow。

## 1. 总体链路

一次插件执行会经过以下层次：

```text
Python handler / JS handler
        │
        │ 业务返回值
        ▼
Python JSON runner（仅 Python）
        │ 统一包装为 { ok, result, notification? }
        ▼
dist/main.js 中的 workflow handler
        │ Python workflow 再包装为运行时 envelope
        ▼
pluginRuntime.executePluginWorkflow
        │ 处理通知，取出 result
        ▼
App.jsx
        │ normalizePluginResults
        ▼
界面结果项 { type, title, data, desc, icon? }
```

JS `action` 不经过 Python JSON runner，但最终也会进入同一个运行时和前端标准化流程。

## 2. 插件业务返回值

插件业务函数可以返回：

| 返回值 | 含义 |
| --- | --- |
| 字符串 | 显示为一条结果，字符串同时作为标题和数据 |
| 数字 | 转成字符串显示，数字同时作为标题和数据 |
| `{title, data, desc}` | 自定义结果标题、数据和描述 |
| 上述值组成的数组 | 显示多条结果 |
| `null`、`None`、空字符串 | 没有结果 |
| 带 `notification` 的对象 | 作为运行时 envelope 处理，通知单独消费 |

例如：

```python
def handler(text, file, config):
    return len(text.upper())
```

这里业务值是数字，例如输入 `abc` 时返回 `3`。它不是一个带 `title` 的对象，前端最后会把它转换成：

```json
{
  "type": "result",
  "title": "3",
  "data": "3",
  "desc": ""
}
```

## 3. Python 的第一层包装：JSON runner

宿主通过 `run_python_plugin` 向 Python 标准输入发送 JSON 请求：

```json
{
  "id": "plugin-id-时间戳",
  "task": "task-2",
  "args": {
    "text": "abc",
    "file": null,
    "config": {}
  }
}
```

Python runner 调用对应的 handler 后，把业务返回值包装成：

```json
{
  "ok": true,
  "result": 3
}
```

如果 handler 抛出异常，包装成：

```json
{
  "ok": false,
  "error": "错误信息"
}
```

Python 的标准输出被 runner 协议占用。插件中的 `print()` 会被重定向到 stderr，因此不会破坏协议 JSON；宿主会把 stderr 记录到前端控制台。

## 4. Python workflow 的 JS 入口包装

向导生成的 `dist/main.js` 会调用：

```js
const response = await context.api.runPython("task-2", {
  text,
  file,
  config
});

if (!response?.ok) {
  throw new Error(response?.error || "Python 执行失败");
}

return {
  ok: true,
  result: response.result,
  ...(response.notification === undefined
    ? {}
    : { notification: response.notification })
};
```

因此 Python workflow 在 JS 运行时中仍然是一个 envelope：

```js
{ ok: true, result: 3 }
```

如果 Python 返回通知，则是：

```js
{
  ok: true,
  result: "已发送 success 通知。",
  notification: {
    level: "success",
    title: "Python 通知测试",
    message: "通知内容",
    durationMs: 5000,
    actions: [
      { type: "close", label: "知道了" }
    ]
  }
}
```

这里的 `ok` 是传输和执行状态，不是要显示给用户的结果字段。

## 5. 运行时拆包

`pluginRuntime.executePluginWorkflow` 收到 JS 入口结果后，会判断它是否是带 `notification` 的 envelope，或是 Python 结果的 `{ok: true, result}` envelope。

拆包规则：

1. `ok !== true` 时抛出执行错误。
2. 取出 `value.result` 作为真正的插件结果。
3. 如果有 `notification`，按通知规则处理。
4. 返回 `result`，交给前端结果标准化。

这一步很关键：如果把整个 `{ok: true, result: 3}` 直接交给结果标准化，它会被误认为一个普通结果对象。因为该对象没有 `title` 和 `data`，标题就会回退为插件名称。当前生成器已经同时兼容“有通知”和“无通知”的 Python envelope。

## 6. 前端结果标准化

`normalizePluginResults(value, plugin.name)` 负责把插件值转换成界面统一结构：

- 字符串或数字：`title` 和 `data` 都使用该值。
- 对象：优先读取 `title`、`label`、`data`、`value`、`desc`、`description`。
- 数组：逐项转换成多条结果。
- 空值：返回空结果列表。

结果对象的 `title` 默认值是传入的插件名称，所以只有在传入了错误的 envelope、或对象本身没有标题时，才会出现“显示插件名称”的现象。

## 7. 通知处理流程

通知必须放在返回对象的 `notification` 字段中：

```python
return {
    "result": "处理完成",
    "notification": {
        "level": "success",
        "title": "处理完成",
        "message": "任务执行成功",
        "durationMs": 5000,
        "actions": [
            {"type": "close", "label": "知道了"}
        ]
    }
}
```

Python runner 会把它转换成：

```json
{
  "ok": true,
  "result": "处理完成",
  "notification": {
    "level": "success",
    "title": "处理完成",
    "message": "任务执行成功",
    "durationMs": 5000,
    "actions": [
      {"type": "close", "label": "知道了"}
    ]
  }
}
```

宿主随后执行以下检查：

- 只有调用方允许结果通知（`allowResultNotification: true`）时才显示。
- 插件 manifest 必须声明 `notification.send` 权限。
- `notification` 必须是对象，不能是数组、字符串或数字。
- `level` 会被拆出并映射到宿主通知 API，常用值为 `success`、`info`、`warning`、`error`。
- 通知消费后，只有 `result` 会继续进入结果列表；通知对象本身不会显示成搜索结果。

如果插件没有声明 `notification.send`，通知不会显示，并会在控制台记录警告。若调用方明确不允许通知，通知也不会弹出，但结果仍会正常返回。

## 8. 普通执行与交互式执行

普通 workflow 执行时，宿主会允许结果通知：

```js
{ allowResultNotification: true }
```

交互式 workflow 在输入变化时会经过防抖调度，通常使用：

```js
{ allowResultNotification: false }
```

这样可以避免用户每输入一个字符就弹出通知。交互式插件仍然可以返回结果列表，通知只在明确允许的执行场景中显示。

## 9. 编写插件时的建议

- 普通结果直接返回字符串、数字或结果对象，不要自行包一层 `{ok, result}`。
- Python handler 需要通知时，返回 `{result, notification}`；不要把通知字段放到结果对象内部的 `data` 中。
- 不要在 Python stdout 打印调试信息；使用 `print()` 即可，runner 会将其重定向到 stderr。
- 修改向导已经生成的插件后，需要重新保存/生成 `dist/main.js`；已经加载的旧 JS runtime 还可能需要重启 Lark。
