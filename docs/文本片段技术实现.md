# 文本片段技术实现

## 概述

文本片段功能用于在 Windows 的普通文本输入场景中展开预设文本。例如，触发符为 `;`、关键词为 `email` 时，用户输入 `;email`，程序会删除这 6 个字符并粘贴对应文本。

该功能不是输入法，也不会拦截或改写所有键盘事件。它使用 `rdev` 注册 Windows 全局键盘监听，在触发符出现后短暂记录后续字符；匹配成功时再通过 `enigo` 模拟退格和 `Ctrl+V`。

当前实现为 Windows 功能。非 Windows 平台的 `start()` 是空实现。

## 配置模型

单个片段使用 `TextSnippet` 表示：

```rust
pub struct TextSnippet {
    pub keyword: String,
    pub text: String,
}
```

文本片段配置保存在现有 `BaseConfig` 中：

```rust
pub snippets_enabled: bool,
pub snippet_trigger: String,
pub text_snippets: Vec<TextSnippet>,
```

对应的 JSON 结构如下：

```json
{
  "snippets_enabled": true,
  "snippet_trigger": ";",
  "text_snippets": [
    {
      "keyword": "email",
      "text": "example@example.com"
    }
  ]
}
```

默认行为：

- 功能默认关闭；
- 默认触发符为 `;`；
- 默认片段列表为空；
- 新增字段使用 `serde(default)`，旧配置文件可以继续读取。

配置文件的实际位置由 `utils::dirs::config_path()` 决定，文本片段没有单独的数据库或配置文件。

## 前后端调用链

### 读取设置

设置页加载时调用：

```text
React useEffect
  → invoke("get_snippet_settings")
  → main.rs::get_snippet_settings
  → config.rs::snippet_settings
  → Config::read_local_config
```

返回值：

```json
{
  "enabled": true,
  "trigger": ";",
  "snippets": [
    { "keyword": "email", "text": "example@example.com" }
  ]
}
```

### 保存设置

用户点击“保存设置”时调用：

```text
React saveSnippets
  → invoke("save_snippet_settings", { settingInfo })
  → main.rs::save_snippet_settings
  → config.rs::save_snippet_settings_data
  → 校验并写入配置文件
  → snippets.rs::update_settings
  → 立即更新运行时配置
```

保存后不需要重启应用。持久化成功后，内存中的监听配置会立即替换。

## 配置校验规则

校验同时存在于前端和 Rust 后端。前端用于即时反馈，后端是最终可信边界。

### 触发符

- 必须恰好包含一个 Unicode 字符；
- 不能是空白字符；
- 默认值为 `;`。

### 关键词

- 长度为 1 到 32；
- 只允许 ASCII 字母、数字、下划线和短横线；
- 不能为空或重复；
- 两个关键词不能互为前缀。

禁止前缀冲突是因为当前采用即时展开。例如同时存在 `mail` 和 `mailto` 时，输入到 `mail` 就会立即展开，后者永远无法到达。

### 替换文本

- 不能为空；
- 当前没有额外长度限制；
- 可以包含换行和 Unicode 文本。

## 启动与运行时配置

应用启动时，`main()` 先读取本地配置，然后执行：

```text
snippets::update_settings(...)
snippets::start()
```

运行时配置存放在：

```rust
static SETTINGS: OnceLock<RwLock<SnippetSettings>>
```

选择该结构的原因：

- `OnceLock` 负责只初始化一次全局容器；
- `RwLock` 允许键盘监听线程读取配置，同时允许设置页保存后整体更新；
- 保存设置时不需要停止并重新创建全局监听器。

`start()` 创建独立线程并调用 `rdev::listen`。该调用持续阻塞，所以不能运行在 Tauri 主线程上。

## 匹配状态机

监听器只处理 `KeyPress`。状态由 `MatchState` 保存：

```rust
struct MatchState {
    buffer: String,
    active: bool,
}
```

状态转换如下：

| 当前状态 | 输入 | 处理 | 下一状态 |
| --- | --- | --- | --- |
| 普通 | 配置的触发符 | 清空缓冲区 | 监听中 |
| 普通 | 其他按键 | 不处理 | 普通 |
| 监听中 | 普通单字符 | 追加到缓冲区并匹配 | 由匹配结果决定 |
| 监听中 | Backspace | 从缓冲区删除一个字符 | 缓冲区为空前保持监听 |
| 监听中且缓冲区为空 | Backspace | 取消监听 | 普通 |
| 监听中 | Escape、回车、Tab、空格、方向键、Home、End、Delete | 清空并取消 | 普通 |
| 监听中 | 完全匹配 | 安排文本展开 | 普通 |
| 监听中 | 至少一个关键词仍以缓冲区开头 | 等待下一个字符 | 监听中 |
| 监听中 | 不存在可能匹配的关键词 | 清空并取消 | 普通 |

匹配使用字符串精确比较，因此关键词大小写敏感。输入不匹配时，已经输入到目标窗口的触发符和字符不会被删除。

## 文本展开时序

当缓冲区完全匹配关键词时，删除数量为：

```text
触发符 Unicode 字符数 + 关键词 Unicode 字符数
```

当前关键词只允许 ASCII，因此关键词的字节长度与字符数量一致；实现仍使用 `chars().count()` 计算退格次数。

完整时序：

```text
检测到完整关键词
  → 重置匹配状态
  → 创建展开线程
  → 等待 45ms
  → 设置 INJECTING = true
  → 模拟 Backspace，删除触发符和关键词
  → 将替换文本写入系统剪贴板
  → 等待 20ms
  → 模拟 Ctrl+V
  → 等待 50ms
  → 设置 INJECTING = false
```

### 为什么等待 45ms

`rdev` 的回调可能在目标控件真正接收到最后一次物理按键之前执行。如果立即模拟退格和粘贴，可能发生以下错误顺序：

```text
删除关键词 → 粘贴文本 → 最后一个关键词字符进入输入框
```

因此展开任务在独立线程中等待 45ms，让最后一个原始按键先传递给目标控件。该数值是当前 Windows 普通输入框上的经验值，不是操作系统提供的完成信号。

### 为什么需要 `INJECTING`

程序模拟的 Backspace、Control 和 V 也可能被全局监听器观察到。全局原子变量：

```rust
static INJECTING: AtomicBool
```

在模拟输入期间暂停事件处理，避免程序处理自己生成的按键。

## 剪贴板处理

替换文本通过 `ClipboardOperator::set_text_for_paste()` 写入系统剪贴板，然后使用 `enigo` 模拟 `Ctrl+V`。

使用粘贴而不是逐字符模拟输入，主要是为了：

- 提高长文本展开速度；
- 降低目标程序漏字符或截断的概率；
- 更好地支持 Unicode 和多行文本。

剪贴板模块会将这次写入标记为 Lark 内部操作，剪贴板监听器在短时间内识别并跳过它，避免替换文本自动进入 Lark 的剪贴板历史。

当前实现会覆盖系统剪贴板，不会在粘贴完成后恢复原剪贴板内容。

## 线程与并发

功能涉及三类执行上下文：

1. Tauri 主线程负责命令注册和应用生命周期；
2. `rdev::listen` 在线程中持续接收全局键盘事件；
3. 每次匹配成功会创建一个短生命周期展开线程。

运行时设置由 `RwLock` 保护。展开前会克隆匹配到的文本，因此后续设置更新不会改变已经安排执行的展开任务。

`INJECTING` 是全局布尔状态，不是展开任务计数器。极短时间内安排多个展开任务时，任务之间可能相互覆盖该状态；当前 UI 和匹配方式没有专门防止这种并发情况。

## 当前行为边界

### 支持

- Windows 普通文本输入框；
- 单字符可配置触发符；
- ASCII 关键词；
- Unicode、多行替换文本；
- 保存后立即生效；
- Backspace 编辑当前匹配缓冲区；
- 无候选前缀时立即结束监听。

### 不保证支持

- 以管理员身份运行且完整性级别高于 Lark 的应用；
- 游戏、远程桌面、虚拟机和使用原始键盘输入的程序；
- 禁止剪贴板或禁止模拟输入的控件；
- 密码框和系统安全界面。

### 已知限制与风险

- 没有识别或排除密码输入框；
- 没有在鼠标点击、切换窗口或切换应用时取消匹配状态；
- 没有匹配超时，输入触发符后长时间不输入仍可能保持监听状态；
- 没有恢复原系统剪贴板；
- 固定 45ms 延迟在特别缓慢的目标应用中仍可能不足；
- 快速连续触发可能产生多个并发展开任务；
- 匹配大小写敏感；
- 不支持以空格或回车作为确认符的延迟展开模式；
- 不支持变量、日期、动态脚本、富文本或图片片段。

## 安全与隐私

监听器能接收全局键盘事件，但当前实现只在触发符出现后把后续字符保存到内存缓冲区，并在不再可能匹配时清空。普通按键内容不会写入配置、数据库或日志。

错误日志只记录监听器启动失败或展开失败，不记录匹配缓冲区和替换文本。尽管如此，由于当前没有密码框排除，启用该功能时仍应把密码输入场景视为已知风险。

## 示例

配置：

```json
{
  "enabled": true,
  "trigger": ";",
  "snippets": [
    {
      "keyword": "email",
      "text": "example@example.com"
    },
    {
      "keyword": "addr",
      "text": "上海市……"
    }
  ]
}
```

输入和结果：

```text
输入：请联系 ;email
结果：请联系 example@example.com
```

不匹配时：

```text
输入：;unknown
结果：;unknown
```

监听器发现没有任何关键词以 `u` 开头后就结束匹配，但不会删除用户已经输入的内容。

## 后续扩展建议

如果继续演进，建议按以下优先级处理：

1. 增加匹配超时，并在窗口切换或鼠标点击时清空状态；
2. 检测密码框或安全输入场景并禁用展开；
3. 串行化展开任务，消除快速连续触发的并发竞争；
4. 在不影响目标程序读取剪贴板的前提下恢复原剪贴板；
5. 将 45ms 延迟变为可测试的内部参数，或寻找目标控件确认输入完成的机制；
6. 根据产品需要增加大小写选项、结束符触发或动态变量。

这些建议不是当前功能契约，实施时需要分别评估兼容性和安全风险。
