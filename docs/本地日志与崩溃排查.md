# 本地日志与崩溃排查

此能力随重新构建、安装后的版本生效。旧安装版不会自动获得日志捕获能力。

## 文件位置

启动时按顺序尝试以下可写目录，并在会话日志首行记录实际使用的目录：

1. `lark.exe` 所在目录下的 `resources/data/logs`，例如 `D:\App\Lark\resources\data\logs`。
2. `%LOCALAPPDATA%\Lark\logs`。
3. `%TEMP%\Lark\logs`。

文件名前缀为 `lark-年月日-时分秒-进程ID`，每次启动单独建文件，便于对应一次闪退。

| 文件 | 内容 |
| --- | --- |
| `.log` | Rust 的 Debug 及以上日志、主进程 stdout/stderr、前端 console、未捕获 JS 错误和 Promise rejection、React 错误，以及 Python 插件结束后读到的 stderr 和异常退出状态 |
| `.panic.log` | Rust panic 的时间、进程、线程、错误位置和强制采集的堆栈，独立于普通日志锁写入 |
| `.crash.txt` | Windows 主进程未处理原生异常的异常码、线程、地址，以及转储是否生成成功 |
| `.dmp` | 原生异常的 minidump，由独立的短命辅助进程生成，用于调试器分析 |

普通日志超过约 10 MiB 时轮转，单会话最多保留 3 份备份。每次启动清理 7 天以前的 `lark-*.log`，并只保留最新 20 份已有日志；本次运行中新生成的文件可能暂时超过这个数量。`.panic.log` 也属于这项清理规则。`.dmp` 和 `.crash.txt` 不自动清理，排查后手动归档或删除。

## 快捷键闪退怎么查

复现后按时间找到同一前缀的文件。日志中的 `[wake]` 会记录快捷键是否认为窗口可见、前端是否收到显示请求、显示和聚焦是否完成，以及是否发生失焦隐藏。先确认进程是否退出，再检查 `.panic.log`、`.crash.txt` 和 `.dmp`；窗口瞬间消失也可能只是失焦隐藏。

release 构建保留 PDB 调试信息。发布时在开发侧保存该安装包对应的 exe 和 PDB，分析转储时必须匹配同一构建。PDB 不需要放进用户安装目录。

## 捕获范围

日志初始化发生在正常应用配置、数据库和 WebView 初始化之前，但进程入口执行前的 DLL 加载失败无法由应用自身记录。没有写日志、又被代码主动忽略的错误也无法自动还原。

前端日志通过 IPC 传给后端，普通消息最多等待 100ms 批量发送，错误立即发送；主进程 stdout/stderr 由读管道线程落盘，因此进程突然终止时，最后少量尚未送达的消息仍可能丢失。

Windows 转储是尽力捕获：强制结束进程、断电、部分 fail-fast、异常处理器被覆盖或严重内存损坏等情况不能保证生成文件。WebView2 是独立进程，其自身的原生崩溃不属于主进程转储范围。Python stderr 在插件执行完成后记录，插件超时或主进程先退出时可能缺失；子进程的独立日志不会被自动合并。此实现保留现有 Python stdout JSON 协议。

## 开发验证

- `node --test scripts/test-diagnostics.mjs`：console、全局错误、重复安装、传输失败和消息长度限制。
- `cargo test --manifest-path src-tauri/Cargo.toml --bin lark utils::diagnostics::tests`：UTF-8 分片、文件轮转及旧日志清理。
- 原生异常和 panic 需要使用独立测试程序验证，避免让正在使用的 Lark 主进程主动崩溃。
